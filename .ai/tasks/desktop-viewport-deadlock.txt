## 一句话描述

desktop hosted terminal 收到本地 viewport 状态后，UI 主线程递归锁定 `TerminalSessionBinding.inner`，导致 Codux 永久卡死且 CPU 很低。

### 复现

实际：两次采样间隔约 16 分钟，主线程始终停在 `TerminalView::render -> TerminalSessionBinding::resize -> parking_lot::RawMutex::lock_slow`。
期望：viewport 状态刷新完成，UI render 返回。
证据等级：A

### 边界

last-known-good：`HEAD 758cedcf`，不含 `refresh_local_viewport_if_current_owner` 新 hosted 分支。
first-wrong：dirty tree 新增 hosted 本地 viewport refresh 分支。
方法：`git diff` 确认新增代码；安装二进制 symbols 与反汇编确认运行构建含该路径。

### 假设

1. 陈述：`if let` scrutinee 创建的 `MutexGuard` 覆盖 `if` 主体，主体调用 `resize()` 时递归锁定同一 mutex。
   预测：二进制先锁 `self.inner`，锁未释放时调用 `resize()`，返回后才尝试解锁。
   判别实验：反汇编 `TerminalView::render` 中内联 refresh 路径。
   结果：锁指令位于 `resize` 调用前，解锁指令位于调用后；现场停在 `resize` 首次锁获取。
   状态：confirmed
2. 陈述：其他后台线程长期持有 `self.inner`。
   预测：采样中存在另一个 binding mutex 等待或持锁调用栈。
   判别实验：检查两次全线程采样。
   结果：未发现；运行线程均处正常等待，仅主线程出现该 binding mutex 等待。反汇编证明自锁即可解释全部现象。
   状态：rejected

### 根因

因果链：viewport event 改变 generation/owner -> render 调用 refresh -> `self.inner.lock().last_resize` guard 保持到 `if` 主体结束 -> 主体调用 `resize()` -> 同线程再次锁 `self.inner` -> 永久等待。
first-wrong condition：managed hosted terminal 已有 `last_resize`，当前 owner 为本地，且 viewport event 使 generation 改变或从 remote 切回 local。
