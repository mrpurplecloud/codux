# 诊断 Gate

## 现象

描述：desktop codux 连 headless host，连接窗口极短且失败占绝大多数；终端无法输入。
频率：2026-09-09 20:02–23:45 期间 controller_connect ok=20 / failed=116（约每 10 分钟才连上一次）。
环境：Peplink SDWAN 关闭；desktop 与 Mac Studio 各自独立上网；桌面端 Clash Verge 处于 GLOBAL 模式。

## 复现

状态：reproduced
方法：用产品真实入口 `codux_remote_transport::RemoteTransportFactory::connect_controller()`（参数取自 desktop 真实 `remote-controllers.json`）在临时探针里拨号，得到与 app 日志一致的失败签名。
实际：
- 23:29–23:31 探针 8/8 成功；23:42–23:44 探针连续 15 次 4s/6s/8s 全超时，45s 预算单拨在 30s 内 `timed out`；00:52–01:07 连续 75 次全部成功（同一 host、同一 relay）。
- 失败时 app 与探针同时失败，成功时同时成功 → 与进程无关，是路径/对端可达性。
- 单条连接可稳定存活 280s（探针），死因是 host 侧 `stream readiness timeout`（探针未开业务流）。
- 「连接被关闭后立即重拨」在探针中 1:1 复现为 3 连超时。
证据等级：A（实际运行 + 复现 + 日志 + 测试输出）

## 边界

last-known-good：Peplink 开启时，desktop 经 SDWAN 直连 host（10.10.10.18:*）可用。
first-wrong：Peplink 关闭后唯一可用路径是 host 自建 relay `iroh-service.dux.plus`，该路径往返 1.2–1.6s 且 host 在其上以分钟级窗口断续可达；desktop 的拨号预算（4/6/8s）、端点生命周期（3 次失败即销毁重建）与退避（上限 60s）按「快速 relay」调参，无法在这条路径上完成/恢复连接。

## 关键证据

1. host 侧健康：`/Users/mac/.codux-agent/status.json`（经产品 file.read 读取）显示 node 78e214f6…、relay=iroh-service.dux.plus、started 2026-09-08T13:49Z；`/ping` 返回 uptimeMs=150943380 → 151909545，与墙钟同步增长（42.2h 无重启）；host.metrics 显示 CPU 空闲。
2. 路由唯一：host 的 DNS 发现记录（`_iroh.xdtbj7oyu....dns.iroh.link` TXT）= 只有 `relay=https://iroh-service.dux.plus/`，无任何直连地址；本地保存的 directAddrs 全是死掉的 SDWAN 地址 10.10.10.18:58619/63360/51038；host 不与本机同局域网（局域网入站 peer 为手机，device ddf47e02=荣耀Magic V3）。
3. 路径慢：relay 路径连接 RTT 1.2–1.6s；TLS 握手 0.7–1.0s（Clash GLOBAL 代理绕行）；对照：手机经 relay 连本机 238–444ms、同局域网直连 8–16ms。
4. 死窗口内我方无故障：relay 的 HTTP 端点全程 1–2s 正常响应；每次重建 endpoint 的 `iroh_controller online=true`（relay 注册成功）。
5. 拨号成本：成功拨号 0.7–1.9s（热），冷启动最长 7.2s（第 3 次尝试 8s 预算内成功）→ 首个 4s 预算经常不够。

## 假设

1. 陈述：host 在其自建 relay 上的可达性分钟级断续（host 侧网络/relay 转发），是本轮「无法连接」的直接原因。
   预测：死窗口内我方 relay 注册正常（已证），relay HTTP 正常（已证），而产物侧任何预算都无法连上（已证 30s 超时）。
   状态：confirmed（对「host 经该 relay 不可达」这一层）；host 腿 vs relay 转发两者未区分。
2. 陈述：产品重连策略把可达性抖动放大为分钟级不可用。
   预测：4s 首拨 + 3 次失败重建 endpoint + 60s 退避 → 恢复时间远大于路径恢复时间。
   状态：confirmed（日志时序 + 探针复现）。

## 根因

因果链：Peplink 关闭 → 记忆地址（SDWAN）全死 + host 不发布直连地址 → 只剩 host relay 一条路 → 该路径慢（1.2–1.6s RTT，代理绕行）且 host 在其上分钟级断续 → 4s 首拨预算常不够 → 3 次失败即销毁/重建 endpoint（再付 4.5–6s 注册）→ 退避至 60s → 用户看到长时间「无法输入」，偶发窗口内连上后 35–136s 又断。
first-wrong condition：连接建立/恢复的预算与端点生命周期策略，与「唯一可用路径」的实际特性（慢、间歇可达）不匹配。
证据等级：A
已确认：true（产品侧策略失配已确认；host 腿 / relay 转发之争未区分，需 host 或 relay 侧证据）
